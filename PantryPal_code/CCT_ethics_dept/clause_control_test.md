| **#**  | **PIPEDA Principle**                     | **Clause (What We Promise)**                                                | **Control (How We Implement It)**                                                                                                                             | **Test (How We Verify It)**                                                                                                                      | **Status**                                                       |
| ------ | ---------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| **1**  | **Accountability**                       | We are responsible for all personal data under our control.                 | Telemetry matrix + ethics ledger document what we store; only two DynamoDB tables hold user data; no hidden third-party flows.                                | **Spec test:** `test_data_inventory_spec` – Verify all data fields in DynamoDB appear in telemetry docs; ensure no extra tables store user data. | ✅ Implemented                                                    |
| **2**  | **Identifying Purposes**                 | Users know why data is collected before providing it.                       | Signup copy + privacy notes explain that email is for login and search history powers suggestions (limited to 10 items + 30-day TTL).                         | **Spec test:** `test_purposes_match_telemetry_spec` – Compare telemetry matrix to Terms/Privacy text for consistency.                            | ✅ Implemented                                                    |
| **3**  | **Consent**                              | Users must consent to data collection and can withdraw consent anytime.     | Signup requires accepting Terms; `/delete_account` removes all user and history data immediately.                                                             | **Spec test:** `test_delete_account_acts_as_withdrawal_spec` – Create test user, call delete, confirm zero remaining records.                    | ✅ Implemented                                                    |
| **4**  | **Limiting Collection**                  | We collect only what is strictly necessary.                                 | `Users` stores only: email, passwordHash, salt, createdAt; `UserSearchHistory` stores only: UserID, timestamp, ingredients, recipesPreview, expiresAt.        | **Spec test:** `test_history_fields_minimized_spec` – Insert history via `/suggest` and assert no unexpected fields exist.                       | ✅ Implemented                                                    |
| **5**  | **Limiting Use, Disclosure & Retention** | Data used only for recipe suggestions; no unnecessary retention or sharing. | No email/UserID ever sent to Spoonacular; last 10 history entries per user kept; **expiresAt** set to enforce 30-day TTL; data never shared with ad networks. | **Spec test:** `test_history_retention_spec` – After >10 suggestions, verify ≤10 records; verify TTL deletes expired items.                      | ✅ Implemented (TTL enabled)                                      |
| **6**  | **Accuracy**                             | Data must be accurate and up to date.                                       | Only personal field is email; users can delete account and re-sign up with updated data; no stale derived attributes.                                         | **Spec test:** `test_recreate_account_updates_email_spec` – Delete + re-signup creates only new email entry.                                     | ✅ Implemented                                                    |
| **7**  | **Safeguards**                           | Personal data must be protected with strong security.                       | Passwords hashed with PBKDF2-SHA256 + salt; HTTPS-only API Gateway; DynamoDB encryption; no logging of email/password; circuit breaker + kill switch.         | **Spec test:** `test_password_not_plaintext_spec` – Assert stored passwordHash is not plaintext and includes salt.                               | ✅ Implemented                                                    |
| **8**  | **Openness**                             | Data practices must be transparent and documented.                          | Public telemetry matrix, ethics ledger, and API docs; clear retention policy.                                                                                 | **Spec test:** `test_docs_cover_all_data_flows_spec` – Ensure every field in DynamoDB is documented.                                             | ✅ Implemented                                                    |
| **9**  | **Individual Access**                    | Users can access or remove their personal information.                      | `/delete_account` removes all user data; history access can be added in future; minimal data stored reduces access complexity.                                | **Spec test:** `test_access_via_support_process_spec` – Validate ability to retrieve + review user records in test environment.                  | 🟡 Partially implemented (erasure supported, access UI deferred) |
| **10** | **Challenging Compliance**               | Users must be able to challenge and correct practices.                      | Users can delete account; privacy practices documented; future version would add formal contact method.                                                       | **Spec test:** `test_delete_account_clears_all_data_spec` – Deleting account clears both tables fully.                                           | ✅ Implemented (challenge process minimal for MVP)                |
